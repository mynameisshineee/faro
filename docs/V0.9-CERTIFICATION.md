# llminbox v0.9 — certificado de la corrida de piloto

Estado: **piloto de un carril ejecutado y revertido con éxito; repetido sobre el
OCI reproducible del candidato OSS integrado**.

Fecha de la evidencia: 2026-09-07. Proyecto Compose:
`llminbox-v09-cert`. Puerto publicado: `127.0.0.1:18099`.

Este documento registra lo que se observó en una corrida real. No sustituye
los tests ni convierte una sola corrida en una garantía de producción. Los
identificadores se conservan porque permiten contrastar la causalidad y el
replay; no se incluyen credenciales, tokens, claves, paths privados ni cuerpos
que puedan contener contexto de la flota.

## Resultado observado

| Fase | Evidencia observada | Veredicto |
|---|---|---|
| arranque nativo | `/live` respondió 200 y `/ready` respondió 503 antes de abrir la admisión | el proceso estaba vivo, pero no se presentó como listo con las barreras cerradas |
| bootstrap | los dos verbos quedaron `open`, ambos en epoch 1; después `/ready` respondió 200 | la apertura fue un único cambio de estado visible y habilitó readiness |
| escritura | evento `evt_89c14407d64d45c8b18ca108f8b614c2`; recibo durable `rcp_4ae444aad19b424288af35e548336d71` | la mutación devolvió identidad de evento y recibo |
| replay | la repetición exacta devolvió el mismo evento y el mismo recibo; el ledger contenía una sola entrada | la repetición no produjo una segunda materialización |
| cierre | los dos verbos quedaron `closed`, ambos en epoch 2 | se cerró nueva admisión antes de drenar y sellar |
| sello | los dos verbos quedaron `sealed`, ambos en epoch 3 | el carril llegó al estado terminal con la cola resuelta |
| certificado | `certified_at=2026-09-07T04:33:58Z`, `pending=0`, `failed=0`, `unresolved=0`, `durable_v=6` | el servidor certificó barreras selladas y outbox vacío en una foto atómica |
| reversión | se quitó la capa nativa y arrancó el compose base con `servicio:app`; quedó `healthy` y el ledger conservó la entrada | la reversión conductual no exigió borrar el estado durable |

Los epochs anteriores corresponden a **ambas** barreras cerradas del contrato:
`events.accept` y `outbox.requeue`. El certificado de rollback no fue compuesto
con varios `GET` del cliente: el Journal autenticó la sesión de operador y leyó
barreras, contadores y `durable_v` en una única transacción.

## Repetición sobre el artefacto OSS integrado

El gate 4.5 se repitió después de integrar el paquete open source, contra la
imagen cargada **desde el OCI producido por `tools/build-release.sh`**, no contra
una reconstrucción local equivalente. El artefacto fuente es el commit
`a0cfc2e28cc895b4bb3a4a915521e16b9e4bdd08`; su SHA-256 es
`66972a1e42eefedabbd481303b8a07ee5b7ca7821dd8bdaf423bbb8c27dfe165`.
Dos builders BuildKit independientes, sin caché, produjeron ese mismo byte
stream.

La repetición usó el proyecto aislado `llminbox-v09-final2` y el puerto
`127.0.0.1:18219`. Observó `503 → 200 → 503` en `/ready`, una sola
materialización durable, replay con el mismo evento
`evt_2978640739334ae99813850387249804` y recibo
`rcp_d859061c29104e8bb015316d5f5d1b3e`, y certificado atómico a
`2026-09-07T05:47:52Z`. Ambas barreras quedaron `sealed` en epoch 3,
`pending=failed=unresolved=0` y `durable_v=6`. Después se retiró la capa
nativa: el compose base arrancó `healthy` sobre los mismos volúmenes y conservó
exactamente esa materialización. Finalmente se eliminaron sólo el contenedor,
la red y los cuatro volúmenes temporales con prefijo `llminbox-v09-final2`; el
expediente redaccionado quedó fuera del repositorio, sin credenciales ni claves.

Este commit documental es el expediente del artefacto anterior; no pretende que
un cambio posterior de documentación tenga el mismo digest OCI. La procedencia
del OCI liga de forma explícita el subject SHA-256 al commit fuente.

## Secuencia reproducible, sin secretos en comandos

Los valores sensibles viven en ficheros privados 0600. El ejemplo usa paths de
marcador; no copies una credencial dentro del historial del shell, el YAML o la
línea de comandos de `curl`.

```sh
export PILOT_ENV=/ruta/privada/llminbox-v09-cert.env
export LLMINBOX_PILOT_PORT=18099
export LLMINBOX_OPERATOR_CREDENTIAL_FILE=/ruta/privada/pilot-operator.credential
export LLMINBOX_WORKLOAD_FILE=/ruta/privada/pilot-workload.credential
export LLMINBOX_API=http://127.0.0.1:18099

docker compose -p llminbox-v09-cert \
  --env-file "$PILOT_ENV" \
  -f docker-compose.pilot-key-init.yml run --rm projector-key-init
docker compose -p llminbox-v09-cert \
  --env-file "$PILOT_ENV" \
  -f docker-compose.pilot-key-init.yml run --rm pepper-init

docker compose -p llminbox-v09-cert \
  --env-file "$PILOT_ENV" \
  -f docker-compose.pilot.yml \
  -f docker-compose.pilot-native.yml config -q
docker compose -p llminbox-v09-cert \
  --env-file "$PILOT_ENV" \
  -f docker-compose.pilot.yml \
  -f docker-compose.pilot-native.yml up -d

curl -fsS http://127.0.0.1:18099/live
curl -i http://127.0.0.1:18099/ready
./llmi admission bootstrap ROLLOUT
./llmi admission status
curl -fsS http://127.0.0.1:18099/ready
```

La segunda llamada a `/ready` debe ocurrir sólo después de comprobar que ambos
verbos están `open` en el mismo carril y epoch. Un `200` en `/live` antes del
bootstrap no autoriza trabajo.

Para reproducir el replay, usa aliases que existan en el roster privado y
ejecuta **exactamente la misma orden**, clave y bytes de stdin dos veces:

```sh
./llmi session open
./llmi post --key pilot-v09-replay-001 \
  <alias-emisor-del-roster> <alias-destino-del-roster> FYI \
  "piloto v0.9" < /ruta/privada/payload-inmutable.md
./llmi post --key pilot-v09-replay-001 \
  <alias-emisor-del-roster> <alias-destino-del-roster> FYI \
  "piloto v0.9" < /ruta/privada/payload-inmutable.md
```

La prueba pasa únicamente si ambas respuestas identifican el mismo evento y
recibo y el ledger tiene una sola materialización. Contar el ledger evita llamar
«replay» a dos respuestas iguales que hayan escrito dos veces:

```sh
grep -F -c 'evt_89c14407d64d45c8b18ca108f8b614c2' \
  "$LLMINBOX_PILOT_LEDGER_HOST/LEDGER.md"
```

El cierre y la reversión se ejecutan en este orden. `seal` no sustituye a
`close`, y un `rollback-status` rojo no se puede saltar con una inspección
manual:

```sh
./llmi admission close DRAIN_FOR_ROLLBACK
./llmi admission status
./llmi admission rollback-status
# Continuar sólo cuando pending=failed=unresolved=0.
./llmi admission seal DRAIN_FOR_ROLLBACK
./llmi admission rollback-certify

docker compose -p llminbox-v09-cert \
  --env-file "$PILOT_ENV" \
  -f docker-compose.pilot.yml \
  -f docker-compose.pilot-native.yml down
docker compose -p llminbox-v09-cert \
  --env-file "$PILOT_ENV" \
  -f docker-compose.pilot.yml up -d
docker compose -p llminbox-v09-cert \
  --env-file "$PILOT_ENV" \
  -f docker-compose.pilot.yml ps
grep -F -c 'evt_89c14407d64d45c8b18ca108f8b614c2' \
  "$LLMINBOX_PILOT_LEDGER_HOST/LEDGER.md"
```

`down` se ejecuta deliberadamente sin `--volumes`: el rollback cambia la
composición y el entrypoint, no borra journal, índice, pepper ni ledger.

## Gaps que el piloto hizo visibles y que se corrigieron

### Ownership de secretos montados por bind

El primer intento de entregar secretos mediante bind no cumplía la propiedad
que el gateway, ejecutado como uid 1000, exige junto al modo 0600. El runtime
falló cerrado, como debía; relajar la comprobación habría convertido una
fricción de Docker en una degradación de seguridad.

La corrección fue introducir inicializadores explícitos para frame key y
pepper. Copian los bytes a volúmenes nombrados separados, de forma atómica, los
dejan con owner `1000:1000` y modo 0600, y el gateway recibe esos volúmenes en
solo lectura. Los inicializadores no sustituyen silenciosamente un secreto ya
instalado por bytes diferentes.

### Roster ausente

La topología inicial montaba el mapa V8, pero no un roster con el que validar su
censo. El gateway no podía demostrar que sus principals y roles pertenecían a
la flota y el arranque se negó correctamente.

La corrección fue hacer explícitos el bind privado del roster y la ruta interna
`LLMINBOX_ROSTER=/state/roster.json`. Mapa y roster se validan antes de abrir el
puerto. El roster enumera agentes y roles —no principals V8— y debe contener al
menos un agente para cada rol que el mapa usa; no se infiere del nombre de una
sesión, del contenedor ni del propio mapa de credenciales.

Ambos fallos fueron de composición, no razones para suavizar el núcleo. Quedan
convertidos en precondiciones reproducibles y cubiertas por pruebas estáticas y
de arranque.

## Qué certifica esta evidencia

- Un runtime nativo de un carril permaneció no-ready hasta una apertura
  explícita por operador.
- Una escritura produjo evento y recibo, y su replay exacto no duplicó la
  entrada del ledger observada.
- El cierre y sello avanzaron conjuntamente las dos barreras mediante epochs.
- El certificado sólo se obtuvo con ambas barreras selladas y los tres
  contadores de outbox a cero.
- La misma topología durable pudo volver al entrypoint base `servicio:app` sin
  perder la entrada observada del ledger.

## Límites: afirmaciones que esta corrida no hace

- No certifica alta disponibilidad, consenso multi-nodo, failover entre hosts
  ni tolerancia a particiones de red.
- No es una prueba de carga, una ventana prolongada de soak ni evidencia sobre
  16 agentes escribiendo concurrentemente.
- No demuestra recuperación frente a pérdida o corrupción física de los
  volúmenes; demuestra que una reversión **sin borrarlos** conserva el estado.
- No demuestra que cualquier payload o cualquier integración externa sea
  idempotente; demuestra el replay exacto del evento identificado arriba.
- No certifica aislamiento entre todos los carriles de una flota real ni una
  auditoría ofensiva completa. Éstas requieren sus controles negativos
  específicos.
- No acredita por sí sola reproducibilidad de imagen, procedencia de artefactos
  o un release público firmado. Es evidencia operacional de v0.9, no una firma
  de supply chain.
- No autoriza reabrir un carril `sealed`: el sello observado es terminal. Otro
  estreno requiere un journal/carril nuevo o el procedimiento de migración que
  se defina explícitamente; no se edita el historial para hacerlo pasar.

En resumen: la corrida demuestra el circuito mínimo completo —fail-closed,
admisión, escritura con recibo, replay, cierre, drenado, sello, certificado y
vuelta al binario base— para una instancia y un carril concretos. Todo lo que
quede fuera de ese perímetro continúa siendo una hipótesis que debe falsarse por
separado.
