# durable_v=7: snapshot y rollback

La migración canónica de producción `durable_v=6 -> 7` no escribe ningún byte
v7 sin haber retenido antes una imagen SQLite consolidada y verificable. El
contrato vive en `Journal.initialize()`, `Journal.migration_snapshot()` y
`Journal.restore_pre_v7_snapshot()`.

## Exclusión y publicación de la imagen

`initialize()` toma el lock de ciclo de vida `.lifecycle` en modo exclusivo
antes de fotografiar. Toda transacción normal de `Journal` toma ese mismo lock
en modo compartido antes de abrir `BEGIN IMMEDIATE` y lo conserva hasta después
de `COMMIT` o `ROLLBACK`. Por tanto, un writer v6 queda enteramente antes de la
imagen o se serializa detrás del commit v7; no existe una ventana donde un
commit aparezca en v7 pero falte en la imagen de rollback.

La imagen se crea mediante la API SQLite backup, se somete a `quick_check` y
`foreign_key_check`, se cierra y se sincroniza a disco. Su nombre incluye un
prefijo del SHA-256 de los bytes. Después se publica atómicamente un manifiesto
`llminbox.migration-snapshot.v1` con el digest completo. Inmediatamente antes
de sellar `durable_v=7`, la migración vuelve a resolver el manifiesto y compara
el digest esperado. Una fuente v6 sin esa evidencia falla cerrada y conserva
su sello v6. Una base creada directamente en v7 no fabrica un pasado ficticio.

## Primitiva de rollback

El rollback no inicia ni simula el binario antiguo. Sólo restaura exactamente
la imagen v6 retenida. Requiere:

- un `Journal` v7 en estado `READY`;
- una sesión válida cuyo principal tenga exclusivamente
  `admission_operator`;
- ambas barreras de admisión en `sealed` para cada carril que aparezca en
  cualquier tabla durable; la ausencia de historial equivale a `closed`, no a
  consentimiento;
- ningún outbox `pending` o `failed` en toda la base;
- el SHA-256 esperado, suministrado fuera de banda y coincidente con el
  manifiesto y con los bytes retenidos.

`restore_pre_v7_snapshot()` cierra las conexiones, acredita cierre y drenado
DB-wide en una transacción, trunca el WAL, verifica que la imagen sigue siendo una v6
exacta y copia esos bytes a un temporal sincronizado. Elimina sidecars SQLite
antes del `replace` atómico para impedir que un WAL v7 se reproduzca sobre la
imagen v6, sincroniza fichero y directorio, y deja el objeto `Journal` en estado
`NUEVO`. El siguiente paso operacional corresponde al binario v6.

## Evidencia focal

`tests/journal/test_schema_v7_fleet_control.py` contiene falsadores para la
retención y digest, el fallo cerrado, la serialización determinista SH/EX y la
igualdad byte a byte tras rollback. Toda ejecución de este módulo debe citar
el SHA exacto del commit probado.
